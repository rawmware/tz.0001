# Tests

## Test 1 - Every TZ answer is copy-ready by default [sanity]
Viewport: mobile
Covers: assistant copy box, one-tap Copy control, plain-text output, instant local tools
Description: Verifies TZ presents answers as clean copy-ready content without requiring the model to emit Markdown fences.

Steps:
1. Enter "What is 77x3" and submit
2. Inspect the assistant response
3. Inspect the response controls

Expected: TZ returns 231 inside a code-style answer box with a visible Copy button; the displayed answer itself does not contain triple-backtick Markdown fence characters.

## Test 2 - Writing requests use the same copy-first surface
Viewport: desktop
Covers: writing workflow, copy-ready answer box, plain-text output
Description: Verifies a deterministic writing request is presented through the same clean copy surface without relying on WebGPU availability in the QA runner.

Steps:
1. Enter "Write the name roman and make it look cool" and submit
2. Inspect the assistant response
3. Inspect the response controls

Expected: TZ returns multiple styled treatments of ROMAN inside the code-style answer box with a visible Copy button and no Markdown code fences.

## Test 3 - Privacy copy accurately describes local browser execution
Viewport: mobile
Covers: privacy disclosure, browser model cache, no manual installer, no hidden cloud fallback
Description: Verifies TZ clearly explains what local means without falsely claiming model bytes never reach the device.

Steps:
1. Open Monitoring
2. Read the privacy statement
3. Inspect Local inference and Model storage

Expected: The page states that local means this device, no account/subscription/manual installer is required, model assets load into browser cache, prompts are not sent or stored by TZ servers, and model storage does not request persistence.

## Test 4 - Default AI path remains local only
Viewport: desktop
Covers: on-device WebLLM routing, hardware telemetry, execution ledger, removal of app-funded AI

## Test 5 - External AI remains visitor-controlled and rejects insecure endpoints
Viewport: desktop
Covers: visitor-supplied external AI, in-tab key handling, HTTPS validation
Description: Verifies cloud AI is optional, visitor-funded, and guarded against insecure endpoints.

Steps:
1. Open Monitoring and Connect AI
2. Enter "http://example.com/v1" as the endpoint with any model/key placeholders
3. Submit the form

Expected: TZ rejects the endpoint and visibly says external AI endpoints must use HTTPS; the page states credentials remain in the browser tab.
