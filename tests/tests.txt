# Tests

## Test 1 - Every TZ answer is copy-ready by default [sanity]
Viewport: mobile
Covers: assistant copy box, one-tap Copy control, plain-text output, instant local tools
Description: Verifies TZ presents answers as clean copy-ready content without requiring the model to emit Markdown fences.

Steps:
1. Enter "What is 77x3" and submit
2. Inspect the assistant response
3. Inspect the response controls

Expected: TZ returns 231 inside a code-style answer box with a visible Copy button; the displayed answer itself does not contain triple-backtick Markdown fence characters.

## Test 2 - Monitoring exposes one WebGPU-first execution path
Viewport: desktop
Covers: deterministic WebGPU-first loading, known supported Qwen WebLLM model, single-model memory policy, CPU/WASM emergency fallback, hardware proof, no model selector
Description: Verifies TZ automatically chooses a compatible production-allowlisted WebGPU build and never warms a second language model alongside it.

Steps:
1. Open Monitoring
2. Inspect Your hardware, Local inference, and TZ execution
3. Inspect the page for a model picker or manual runtime selector

Expected: Monitoring states WebGPU is the default, shows a Qwen2.5 0.5B WebLLM build as the primary model when compatible, states only one language model is loaded at a time, identifies SmolLM2 135M as the CPU/WASM emergency model, and presents no model picker.

## Test 3 - A failed local runtime has a visible retry and safe diagnostic
Viewport: mobile
Covers: local runtime recovery, Retry local engine control, copyable device diagnostic, diagnostic privacy
Description: Verifies users can recover from a device-specific initialization failure and copy useful runtime facts without leaking prompts or credentials.

Steps:
1. Open Monitoring
2. Inspect the TZ execution controls
3. Click Copy diagnostics

Expected: Retry local engine and Copy diagnostics controls are visible, and the status confirms the copied diagnostic contains no prompt text or API key.

## Test 4 - External AI is an opt-in fallback rather than the default route
Viewport: desktop
Covers: local-first routing, visitor-supplied external fallback, execution disclosure, in-tab key handling
Description: Verifies connecting external AI does not replace instant or on-device execution.

Steps:
1. Open Monitoring and click Connect fallback
2. Enter "https://example.com/v1" as the endpoint, "example-model" as the model, and "example-key" as the key
3. Submit the fallback form and inspect the status text

Expected: TZ says the external fallback is connected, the key is held in memory for the tab, and TZ will still try instant and on-device execution first.

## Test 5 - External fallback rejects insecure endpoints
Viewport: desktop
Covers: HTTPS validation, external provider guardrail, connection form behavior
Description: Verifies visitor-supplied cloud fallback cannot be configured with an insecure endpoint.

Steps:
1. Open Monitoring and click Connect fallback
2. Enter "http://example.com/v1" as the endpoint with any non-empty model and key placeholders
3. Submit the form

Expected: TZ rejects the endpoint and visibly says external AI endpoints must use HTTPS.
